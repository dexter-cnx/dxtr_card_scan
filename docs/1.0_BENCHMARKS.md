# 1.0 Benchmarks

This document defines the reproducible processor benchmark used for the 1.0 release gate.

## Scope

The benchmark intentionally measures native processor work separately from camera/UI latency:

- `quality_decode_and_analysis` — decode the same encoded input and run the Rust quality analysis path.
- `detect_warp_and_ocr_process` — run the full encoded-image processor using the OCR-oriented 1.0 profile shape: auto-detect, perspective warp to a 1600 px long edge, OCR enhancement, maximum dimension 2000, JPEG quality 92.

Camera startup, Flutter widget work, file picking, confirmation UI, and OCR-network/API latency are outside this benchmark.

## Input

`rust/examples/benchmark_processor.rs` generates a deterministic 1600x1000 PNG entirely in memory. It contains a bright card-like rectangle, repeatable texture, and dark horizontal details so edge and quality paths receive stable image structure without depending on external fixtures.

The harness performs one warm-up invocation before timing and reports total elapsed time plus mean milliseconds per operation.

## Run locally

```bash
cargo run --release \
  --manifest-path rust/Cargo.toml \
  --example benchmark_processor -- \
  --iterations 20
```

Use the same commit, Rust toolchain, build profile, input dimensions, and iteration count when comparing results. Absolute timings from different machines are not directly comparable; use them as per-machine baselines and regression signals.

## CI smoke

CI runs three release-mode iterations. This is primarily a build/execution guard and a convenient reference sample, not a statistically rigorous performance threshold. A release baseline should use more iterations on known hardware and record the machine/OS/toolchain.

## Initial 1.0 CI reference baseline

The first green benchmark reference was captured from CI run **#363** on the PR #47 head commit `4c0cbda86a9192dfd9baf3b307987c8ea90e4da8` before squash merge.

Environment:

- GitHub-hosted Ubuntu 24.04.4 runner (`ubuntu-24.04`, image `20260823.283.1`)
- `rustc 1.98.0 (88d9e12ae 2026-08-18)`
- host `x86_64-unknown-linux-gnu`
- release profile, optimized
- deterministic 1600x1000 synthetic PNG, 32,247 bytes
- 3 timed iterations after one warm-up

Reference output:

```text
quality_decode_and_analysis: total=151.47ms mean=50.49ms/op
detect_warp_and_ocr_process: total=465.76ms mean=155.25ms/op
```

These values are **reference observations, not pass/fail thresholds**. GitHub-hosted runner performance can vary between machines and over time. Use the harness to detect large regressions, then reproduce suspicious changes on the same known hardware with at least 20 iterations before treating them as performance regressions.

## Comparison policy

When publishing or reviewing later numbers:

1. Record the commit, OS, CPU/runner type, Rust toolchain, build profile, input size, and iteration count.
2. Compare only like-for-like environments where possible.
3. Treat CI smoke values as trend evidence, not a hard service-level objective.
4. Use a longer local/device run before making optimization claims.
5. Keep quality analysis and full processing results separate; combining them obscures which stage regressed.

The 1.0 benchmark gate is considered complete because the repository now has a reproducible harness, CI execution coverage, and a recorded reference baseline. Future performance work can extend this with device-specific and larger-sample baselines without changing the 1.0 compatibility contract.

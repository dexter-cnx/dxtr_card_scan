# 1.0 API Stability Sign-off

This sign-off records the package API contract that is intended to remain source-compatible through the 1.x line. It does not claim that physical calibration or every platform validation item is complete; those remain separate roadmap gates.

## Primary import

Normal applications should import:

```dart
import 'package:dxtr_card_scan/dxtr_card_scan.dart';
```

The root barrel intentionally exposes the application-facing capture, gallery, processing, profile, template, geometry, theming, native-scanner contract, reusable overlay, and result/configuration APIs. Low-level lifecycle/state-machine orchestration is not part of this primary compatibility surface.

## Advanced import

Custom integrations that need package orchestration internals should import:

```dart
import 'package:dxtr_card_scan/dxtr_card_scan_advanced.dart';
```

The advanced barrel re-exports the primary API and additionally exposes the auto-capture policy/state machine, capture pipeline, stability tracker, live camera session/coordinator/analyzer, feedback controller, and listener-layer UI.

## Root-barrel declaration audit

Every export in `lib/dxtr_card_scan.dart` was reviewed at file/declaration level. The root surface is intentionally composed of these groups:

- capture confirmation/orientation policy
- `CardAutoCaptureConfig` only from the auto-capture policy file
- unified camera/gallery view and camera-image adapter DTOs
- capture controller, controls, image/result/quality metadata
- capture profiles and profile-driven view factory
- native scanner contract/result
- gallery capture/crop and generic crop selection/style/view
- capture frame and frame style
- normalized/captured/preview/camera geometry types
- processor detection, perspective analysis, quality analysis, processor/options
- `CardTemplate`, named regions, extractor/results
- camera/card theme and controls style
- corner-confidence feedback model and reusable overlay
- capture/gallery labels

Low-level orchestration files are not exported by the root barrel. The single `show CardAutoCaptureConfig` export is deliberate because `CardCaptureView` exposes that type directly.

## Neutral naming audit

Public package source was checked for unintended `Dxtr`-prefixed declarations. No such public declaration remains. The package name may contain `dxtr_card_scan`; public Dart types and member names remain product-neutral.

## Intentional 1.0 defaults

The following defaults are compatibility decisions, not incidental implementation details:

- `CardCaptureView` remains `const`-constructible.
- Built-in auto-capture remains disabled by default.
- `CardCaptureResult.qualityMetadata` remains optional.
- Capture profiles do not silently enable auto-capture.
- `CardCaptureProfile.<profile>.captureView(...)` applies profile defaults at runtime while explicit `processOptions` and `autoCapture` arguments override them.
- Live streaming remains opt-in through an explicit transform resolver; unresolved orientation/mirroring does not guess.
- Native scanner support remains dependency-injected and optional.
- Scanner cancellation remains `null`; successful scanner sessions preserve page order.
- `CardTemplate` coordinates remain normalized over the perspective-corrected card image.
- `CardTemplateExtractor` consumes an already-corrected encoded image and does not perform a second detection/perspective pass.
- Root and advanced import paths remain distinct compatibility surfaces.

## Compatibility guardrails

`test/public_api_boundary_test.dart` guards the root/advanced split and primary construction paths. Existing focused tests continue to exercise advanced policy, stability, live coordinator, feedback, and calibration consumers through `dxtr_card_scan_advanced.dart`.

Future 1.x changes should avoid removing or renaming root-barrel declarations, changing constructor requirements/defaults, or moving primary declarations to the advanced barrel without a deprecation/migration path. Advanced APIs are supported public integration APIs, but their separation allows lifecycle/state-machine evolution without making them part of the minimal application-facing surface.

## Sign-off

The public API stabilization gate is complete for 1.0 planning. This sign-off does not close the remaining release gates for physical calibration evidence, Android/iOS/macOS validation, benchmarks, example completeness, or package documentation.

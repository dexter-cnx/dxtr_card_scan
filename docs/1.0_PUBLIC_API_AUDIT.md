# 1.0 Public API Audit

This document inventories the current package barrel before a 1.0 stability promise is made.

## Stability rule

Anything exported by `lib/dxtr_card_scan.dart` is treated as public Dart API by package consumers. Dart exports expose every public declaration in the exported file, not only the headline class that motivated the export. Before 1.0, each exported declaration should therefore be deliberately classified as one of:

- **Primary** — normal application-facing API that should receive source-compatibility protection after 1.0.
- **Advanced** — supported extension/integration API, public by design, but expected to be used by fewer hosts.
- **Internal candidate** — implementation machinery currently exported from the barrel that should be reviewed before a 1.0 compatibility promise.

The audit does not remove or rename API. It defines the decision boundary for follow-up compatibility work.

No removal is performed in this audit. A follow-up PR should choose one of these approaches for each internal candidate declaration:

1. keep it in the root barrel and explicitly support it as advanced public API;
2. move it to a separately documented advanced library before 1.0; or
3. stop exporting it from the public package surface before the 1.0 compatibility contract begins.

## Compatibility observations

- Existing `const CardCaptureView(...)` construction is an established compatibility constraint and must remain covered by regression tests.
- Built-in capture profiles must continue to leave auto-capture disabled until physical calibration evidence promotes production thresholds.
- `CardCaptureResult.qualityMetadata` is optional and should remain source-compatible for existing callers.
- Native scanner support is dependency-injected; the package core should not acquire a mandatory VisionKit, ML Kit, or equivalent SDK dependency.
- CardTemplate coordinates are defined over the perspective-corrected card image. Runtime normalized-bound validation is part of that public contract.
- `CardTemplateExtractor` is a post-process over corrected encoded image bytes and must not silently perform a second detection/perspective-correction path.

## 1.0 exit criteria for API stability

- [ ] Decide the root-barrel disposition of every internal-candidate declaration, including companion types/callbacks exposed by each exported file.
- [ ] Re-audit every root-barrel export at declaration level so no companion public declaration remains unclassified.
- [ ] Add an API compatibility regression suite for the primary construction paths.
- [ ] Document which advanced APIs are supported public contracts.
- [ ] Confirm all public names are neutral and contain no unintended package-specific `Dxtr` prefixes.
- [ ] Confirm public constructors/configuration defaults are intentional for 1.0.
- [ ] Only then mark `stable public API` complete in `docs/ROADMAP.md`.
